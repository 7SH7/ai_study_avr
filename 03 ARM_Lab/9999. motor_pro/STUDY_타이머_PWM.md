# 학습 정리 — STM32 타이머 & PWM 기초

> STM32F411 모터 제어 프로젝트(`9999. motor_pro`) 학습 노트
> 대상: 일반 타이머(시간 측정) → PWM(모터 구동)
> 이 보드 `TIMXCLK = 96MHz` (SYSCLK 96 → PCLK1 48 → 타이머 ×2 보정 = 96MHz)

---

## 0. 큰 그림

타이머의 본체는 **`CNT`(카운터) 레지스터 하나**다. 클럭이 올 때마다 CNT가 +1 되는 게 전부.
나머지 레지스터(PSC, ARR, CCR...)는 전부 **"이 CNT를 어떻게 셀지"** 를 꾸며주는 조연이다.

```
TIMXCLK(96MHz) ──[PSC로 분주]──> CK_CNT ──> CNT +1 ──[ARR 도달]──> UEV(리셋/플래그)
```

---

## 1. 계란판 비유 (핵심 멘탈 모델) 🥚

세 개념을 계란으로 이해하면 안 헷갈린다.

| 개념 | 계란 비유 | 질문 | 이 예시 값 |
|---|---|---|---|
| **CLK** | 계란 | 1초에 계란 몇 개 들어와? | 96,000,000개/초 (고정) |
| **분주비** | 계란 몇 개로 1판? | 계란 **몇 개** 모여야 CNT +1? | 48 (내가 정함) |
| **CK_CNT** | 1초에 몇 판? | 1초에 CNT가 **몇 번** 올라가나? | 96,000,000 / 48 = 2,000,000 |

```
clk:  |1|2|3| ... |48|  |1|2| ... |48|
       \____ 48개 ____/
                ↓ 다 모이면
CNT:          +1              +1
```

### ⚠️ 헷갈림 방지 포인트
- **"몇 개 와야 +1"** = 분주비 (48). ← 클럭 개수
- **"1초에 몇 번 +1"** = CK_CNT (2,000,000). ← 초당 카운트 수(주파수)
- 이 둘은 **다른 질문**이다. 같은 사실을 "개수 관점" vs "초 관점"으로 본 것.
- 검산 팁: `96,000,000 / 48`을 하는 순간 이미 "초당 개수"를 구한 것 → 결과(2,000,000)는 CK_CNT.

## 2. 시간 → 숫자 변환 (타이머 만들기의 핵심)

"96MHz를 내가 원하는 타이머로 바꾼다" = **결정 2개**.

### 결정 1️⃣ — 분주비(PSC): "1카운트를 얼마로 할까"

CK_CNT = 2,000,000이면 → **1카운트(1판) = 1 / 2,000,000초 = 0.5us**.

### 결정 2️⃣ — ARR: "몇 판 세고 끝낼까"

원하는 시간을 1카운트 시간으로 나눈다.
```
목표 = 20ms = 20,000us
1카운트 = 0.5us
→ 필요 판 수 = 20,000 / 0.5 = 40,000판
```

### ⭐ -1을 넣는 이유 (PSC, ARR 공통)

CNT는 **0부터** 센다. 그래서 하드웨어가 내부에서 **자동으로 +1** 보정한다.

```
3판 세고 싶으면 → CNT는 0, 1, 2 (최댓값 2) → ARR = 3 - 1 = 2
세고 싶은 개수:  1  2  3  ...  N
CNT 최댓값(ARR): 0  1  2  ... N-1
```

- `PSC = 분주비 - 1` (48분주 → 47). 하드웨어가 `PSC+1`로 나눔.
- `ARR = 판 개수 - 1` (40,000판 → 39,999). 하드웨어가 `ARR+1`판을 한 주기로 셈.
- -1 안 하면 딱 1카운트(0.5us)만큼 길어짐. 측정에선 미미하나 PWM 주파수에선 신경 써야 함.

## 3. 코드로 옮기기 — 3 STEP

모든 타이머 코드는 이 3스텝이다.

### STEP 1 — 전원 + 숫자 넣기
```c
Macro_Set_Bit(RCC->APB1ENR, ?);   // 타이머 클럭 ON (TIM5=bit3, TIM2=0, TIM3=1, TIM4=2)
TIMx->PSC = 47;                    // 48분주
TIMx->ARR = 39999;                 // 40,000판 = 20ms
```

### STEP 2 — 적용 + 청소
```c
Macro_Set_Bit(TIMx->EGR, 0);      // UG: PSC/ARR "지금 적용!" (섀도우 레지스터 강제 반영)
Macro_Clear_Bit(TIMx->SR, 0);     // 이전 UIF 플래그 청소
```

> **왜 EGR(UG)?** PSC/ARR은 "예약 서랍(섀도우 레지스터)"이 따로 있어 다음 UEV 때 반영된다.
> 처음 세팅 땐 UEV가 아직 없으니, UG로 UEV를 강제로 한 번 일으켜 즉시 반영시킨다.

### STEP 3 — 시작 + 확인
```c
Macro_Set_Bit(TIMx->CR1, 0);      // CEN: 카운터 ON

// (A) 폴링으로 확인
while(Macro_Check_Bit_Clear(TIMx->SR, 0));  // UIF 뜰 때까지 대기 = 시간 경과

// (B) 인터럽트로 받기
Macro_Set_Bit(TIMx->DIER, 0);     // UIE: UEV 나면 인터럽트
NVIC_EnableIRQ(?);                // NVIC에서도 허용 (2단 스위치)
```

### 3스텝 요약
| STEP | 하는 일 | 레지스터 |
|---|---|---|
| 1 | 전원 + 시간→숫자 계산해 넣기 | RCC, PSC, ARR |
| 2 | 계산값 적용 + 플래그 청소 | EGR, SR |
| 3 | 시작 + 끝났는지 확인 | CR1(CEN), SR / DIER |

## 4. 내 컨벤션 (`#define` 스타일)

> 이 프로젝트에서 **TICK = 분주비(클럭 개수)** 로 쓴다. (내 방식 고수)

```c
#define TIMx_TICK        (48)                  // 몇 개 클럭이 1판? (= 분주비)
#define TIMx_FRAG        (TIMXCLK / TIMx_TICK)  // 초당 몇 판? (= CK_CNT) = 2,000,000
#define TIMx_PLS_OF_1ms  (TIMx_FRAG / 1000)     // 1ms당 몇 판? = 2,000
```
```c
TIMx->PSC = (unsigned int)(TIMXCLK / TIMx_FRAG + 0.5) - 1;  // = 48-1 = 47
TIMx->ARR = (TIMx_PLS_OF_1ms * time - 1);                  // time=20 → 40,000-1 = 39,999
```

### ⚠️ 기존 `timer.c`와 TICK 의미가 다름 (주의)
| | 내 방식 | 기존 timer.c |
|---|---|---|
| `TICK` 뜻 | 48 = 클럭 **개수**(분주비) | 20 = **시간**(us) |
| 유도 | `FRAG = TIMXCLK / TICK` | `FREQ = 1000000 / TICK` |

둘 다 CK_CNT는 맞게 나온다. 단 기존 TIM2/TIM4 코드를 읽을 땐 `TICK`이 "us 시간"임을 기억.
**한 파일 내 일관성만 지키면 됨.**

## 5. PWM = 일반 타이머 + CCR

### 핵심 아이디어
일반 타이머(40,000판마다 한 바퀴)에 질문 하나만 추가:
> **"40,000판 세는 동안, 몇 판째까지 불(출력)을 켜둘까?"** → 그게 **CCR**.

```
한 주기 = 40,000판
        │◄──── High ────►│◄──── Low ────►│
CNT:    0 ──────────────► CCR ──────────► 40,000(리셋)
```

- CNT가 CCR을 넘으면 High→Low.
- **듀티 = CCR / (ARR+1) = CCR / 40,000** → 이게 모터 속도.

| CCR | 듀티 | 모터 |
|---|---|---|
| 10,000 | 25% | 느리게 |
| 20,000 | 50% | 중간 |
| 30,000 | 75% | 빠르게 |

### ⚠️ 듀티 vs CCR — 개수 vs 비율 (헷갈림 주의)
- **CCR** = "몇 판까지 High" → **절대 개수** (예: 20,000)
- **듀티** = "전체 중 몇 %가 High" → **비율** (예: 50%)
- **CCR 자체가 듀티가 아니다.** CCR을 ARR로 나눠야 듀티(%)가 나온다.

```
CCR = 20,000, ARR+1 = 40,000  →  듀티 = 20000/40000 = 50%
CCR = 20,000, ARR+1 = 80,000  →  듀티 = 20000/80000 = 25%   (같은 CCR, 다른 듀티!)
```
같은 CCR이라도 전체 주기(ARR)가 다르면 비율이 달라진다.
→ **듀티 = CCR / (ARR+1)**. CCR은 개수, 듀티는 비율. (비유: "50개 중 25개" = CCR 25 = 듀티 50%)

### 듀티 = 모터 속도 (원리)
모터는 20kHz 껌뻑임을 못 따라가고 **평균 전압**으로 반응 → 듀티 = 평균전압 = 속도.
```
듀티 100% → 평균 100% → 최고속 |  듀티 50% → 절반속도 |  듀티 0% → 정지
```

### 듀티 해상도 = ARR+1
CCR은 0 ~ ARR까지 → 속도를 **(ARR+1)단계**로 조절 가능 = 해상도.
ARR 클수록(=분주 최소) 곱게 나뉨. (분주 키우면 ARR 작아짐 → 해상도 손해)
※ 해상도는 **ARR만** 정한다. CCR 크기와는 무관 (CCR은 "지금 듀티 값"일 뿐).

### ⚠️ FRAG(초당 판) vs ARR+1(한 주기 판) — 절대 헷갈리지 말 것
PWM엔 "판 수"가 두 종류라 자꾸 헷갈린다. **완전히 다른 값**이다.

| | 뜻 | 값(예, PSC=0) |
|---|---|---|
| **FRAG (CK_CNT)** | **1초에** 만드는 판 수 (계속 나오는 총량) | 96,000,000 |
| **ARR+1** | **파형 한 번(1주기)** 당 판 수 (한 주기 크기) | 4,800 |

- FRAG = "1**초**에 몇 판"
- ARR+1 = "파형 **한 번** 돌 때 몇 판"

관계식 (파형이 1초에 f_PWM번 반복되므로):
```
ARR+1 = FRAG / f_PWM = 96,000,000 / 20,000 = 4,800   →  ARR = 4,799
```
즉 **ARR+1 = FRAG를 f_PWM으로 나눈 것.** FRAG 그 자체가 ARR+1이 아니다.
(둘이 같으려면 f_PWM=1Hz, 즉 파형이 1초에 딱 1번일 때뿐.)

### PWM의 "3개 주파수" 정리 → 어느 레지스터로

| 이름 | 뜻 | 레지스터 | PWM(모터) 값 |
|---|---|---|---|
| **분주비(TICK)** | clk 몇 개당 CNT+1 | `PSC + 1` | 1 (PSC=0) |
| **CK_CNT(FRAG)** | 1초에 CNT 몇 번 | (자동) | 96MHz |
| **f_PWM** | 파형 1초에 몇 번 반복 | `ARR+1 = FRAG/f_PWM` | 20kHz → ARR=4799 |

### CCR = "속도 다이얼" (언제 0이 아니게 하나?)
CCR은 특별한 케이스에만 바꾸는 게 아니라, **속도를 정할 때마다 바꾸는 상시 손잡이**다.
```
CCR = 0       →  duty 0%    →  모터 정지
CCR = 2,400   →  duty 50%   →  절반 속도
CCR = 4,799   →  duty ~100% →  최고속
```
- **Init에서 CCR=0** → "처음엔 정지로 시작"
- **Set_Duty로 CCR 올림** → "이 속도로 돌아라"
- **버튼/USART로 속도 바꿀 때마다** → CCR 갱신

즉 "CCR을 0이 아니게 하는 경우" = **모터를 돌리고 싶을 때(원하는 속도만큼)**. 켜려면 CCR>0, 끄려면 CCR=0.

### 추가되는 레지스터
| 레지스터 | 역할 |
|---|---|
| **CCR** | 문턱값 (몇 판까지 High) = 듀티 |
| **CCMR** | 채널을 PWM 모드로 (`0x60` = PWM mode 1) |
| **CCER** | 채널 출력 **켜기** (CCxE 비트) |
| **GPIO AF** | 핀을 타이머에 넘김 (GP출력 → Alternate Function) |

### 코드 (TIM5, PA0=CH1, AF2)
```c
// ① GPIO를 AF로 (핀을 타이머가 조종)
Macro_Set_Bit(RCC->AHB1ENR, 0);                 // GPIOA 클럭
Macro_Write_Block(GPIOA->MODER, 0x3, 0x2, 0);   // PA0 → AF 모드(10)
Macro_Write_Block(GPIOA->AFR[0], 0xf, 0x2, 0);  // PA0 → AF2 (TIM5_CH1)

// ② 일반 타이머 부분 (주파수/주기)
Macro_Set_Bit(RCC->APB1ENR, 3);   // TIM5 클럭
TIM5->PSC = 47;
TIM5->ARR = 39999;

// ③ PWM 전용
Macro_Write_Block(TIM5->CCMR1, 0xff, 0x60, 0);  // CH1 PWM mode 1
Macro_Set_Bit(TIM5->CCER, 0);                   // CH1 출력 ON (CC1E)
TIM5->CCR1 = 10000;                             // 듀티 25%

// ④ 적용 + 시작
Macro_Set_Bit(TIM5->EGR, 0);
Macro_Set_Bit(TIM5->CR1, 0);
```
→ 이후 **CCR1 값만 바꾸면 모터 속도 실시간 조절.**

### ⚠️ 모터는 주파수를 다시 골라야
20ms 주기 = **50Hz**는 DC 모터엔 너무 느림(떨림/소음). 모터는 보통 **1~20kHz**.
바꾸는 법은 동일 — PSC/ARR만 재계산:
```
20kHz 원하면 → K = 96e6 / 20,000 = 4,800 → PSC=0(분주 안 함), ARR=4,799
듀티 = CCR / 4,800 (속도 4,800단계)
```
개념은 100% 동일, **PSC/ARR 숫자만 주파수에 맞게 다시 뽑을 뿐.**

## 6. 마스터 공식 (검산용)

```
UEV 주기 = (PSC+1) × (ARR+1) / TIMXCLK
```
20ms 검산: `(47+1) × (39999+1) / 96,000,000 = 48 × 40,000 / 96e6 = 0.02초 = 20ms ✓`

PWM 주파수 = 1 / UEV주기, 듀티 = CCR / (ARR+1).

## 7. 분주비를 어떻게 정하는가 — 체계적 방법 ⭐

> **"내 맘대로 정해도 된다"는 반만 맞다.**
> 정확히는 **"가능한 범위 안에서는 자유롭고, 범위 밖은 불가능하다."**
> 그 범위를 계산하는 것이 이 절의 핵심이다.

### 7-1. 분주비를 양쪽에서 조이는 두 제약

```
분주비 너무 작음 ← ────[ 가능 범위 ]──── → 분주비 너무 큼
  타이머가 빠름                            타이머가 느림
  ARR이 폭을 넘침 ✗                        해상도 거침 / PSC 한계 ✗
```

| 제약 | 이유 | 식 |
|---|---|---|
| **하한** (최소 분주비) | ARR이 타이머 폭(16/32비트)을 **넘치면 안 됨** | `분주비 ≥ 목표시간 × TIMXCLK / ARR_MAX` |
| **상한** (최대 분주비) | **PSC도 16비트**라 최대 65,536 | `분주비 ≤ 65,536` |

### 7-2. ⭐ 핵심 비유 — 16비트 타이머는 **"예산 65,536칸"**

```
목표시간 = 1틱 × 칸수        (칸수 = ARR+1)
제약     : 칸수 ≤ 65,536     ← 이게 예산
```

- **틱을 작게** 하면 → 칸을 **많이** 써야 함 → 예산 초과 위험
- **틱을 크게** 하면 → 칸이 **적게** 필요 → 예산 여유, 대신 거칠어짐

**500ms를 만들 때 예산 사용률:**

| 1틱 | 필요 칸수 | 예산(65,536) 사용률 | 판정 |
|---|---|---|---|
| 0.5us (분주비 48) | 1,000,000 | **1,526 %** | ❌ 초과 |
| 10us (분주비 960) | 50,000 | 76 % | ✅ 꽉 참 |
| **20us (분주비 1,920)** | **25,000** | **38 %** | ✅ **균형** |
| 100us (분주비 9,600) | 5,000 | 7.6 % | ✅ 여유 많음 |

→ 이것이 "48분주로는 500ms를 담을 수 없다"의 정확한 의미다.

### 7-3. ⭐⭐ "해상도가 충분하다"는 무슨 뜻인가

**해상도(1틱) = 타이머가 시간을 쪼개서 볼 수 있는 최소 단위**다.
즉 "시간을 얼마나 잘게 나눠서 표현할 수 있나"이며, **자(ruler)의 최소 눈금**과 같다.

```
1틱 = 20us  →  시간을 20us 단위로만 표현 가능
               500ms를 만들면 실제 오차는 최대 ±20us
```

#### 판단 기준 — 1틱이 "목표 시간에서 신경 쓸 필요 없을 만큼 작은가"

정량적으로는 **`1틱 / 목표시간` 비율**로 본다.

| 1틱 | 목표 500ms 대비 비율 | 판정 |
|---|---|---|
| 20us | 0.004 % | 넘치게 충분 (사람이 절대 인지 못 함) |
| 100us | 0.02 % | 충분 |
| 1ms | 0.2 % | 충분 |
| 10ms | 2 % | 애매 (500ms가 490~510ms로 흔들릴 수 있음) |
| 100ms | 20 % | ❌ 부족 (400/500/600ms로만 표현) |
| 1초 | 200 % | ❌ 500ms를 아예 표현 불가 |

**대략적 지침: 1틱이 목표시간의 1 % 이하면 대체로 충분, 0.1 % 이하면 넉넉하다.**

#### 자 비유로 보면

| 상황 | 비유 |
|---|---|
| 500ms를 20us 눈금으로 | 5 m를 **0.2 mm 눈금 자**로 재는 것 → 과할 정도로 정밀 |
| 500ms를 100ms 눈금으로 | 5 m를 **1 m 눈금 자**로 재는 것 → 너무 거칠어 쓸 수 없음 |

#### 그리고 "충분"의 기준은 **응용이 요구하는 정밀도**에 달렸다

| 응용 | 요구 정밀도 | 필요한 틱 |
|---|---|---|
| **모터 500ms 정지** | 사람이 인지하는 한계가 대략 10 ms 수준 | 20us~1ms면 **넘치게 충분** |
| PWM 듀티 제어 | 듀티 단계 수(해상도)가 곧 속도 단계 | 최대한 촘촘히 (PSC=0) |
| UART 비트 타이밍 | 비트 시간의 수 % 이내 | us 단위 |
| 초 단위 시계 | 1초의 0.1 % → 1 ms | 1ms면 충분 |

**즉 "20us면 500ms에 충분하다"의 의미는:**
> 20us 오차는 500ms의 0.004 %에 불과하고, 모터를 500ms 멈추는 응용에서
> 20us 차이는 **사람도 시스템도 전혀 구별할 수 없다**. 그래서 이보다 더 촘촘하게
> 만들려고 예산(65,536칸)을 낭비할 이유가 없다.

반대로 **더 거칠게 가면** 예산은 남지만, 어느 지점부터는 목표 시간을 정확히 만들 수 없게 된다.
그래서 **"범위 안에서, 필요한 만큼만 촘촘하게"** 가 최적이다.

### 7-4. 5단계 절차 (측정 · 타임아웃 타이머)

**예제: 500 ms, TIM4(16비트), TIMXCLK = 96 MHz**

**① 하한 계산 (범위 제약) — 반드시 계산할 것**
```
분주비 ≥ 목표시간 × TIMXCLK / ARR_MAX
        = 0.5 × 96,000,000 / 65,535
        = 732.4
→ 733 이상
```

**② 상한 확인**
```
분주비 ≤ 65,536   (PSC가 16비트)
```

**③ 범위 안에서 "틱이 깔끔한 값"을 고른다**

| 원하는 틱 | 필요 분주비 | 733~65,536 범위 안? |
|---|---|---|
| 1us | 96 | ❌ (하한 미달) |
| 10us | 960 | ✅ |
| **20us** | **1,920** | ✅ |
| 100us | 9,600 | ✅ |
| 1ms | 96,000 | ❌ (상한 초과) |

**④ `TIMXCLK`의 정수 약수인지 확인** (PSC 오차 0)
```
96,000,000 / 960   = 100,000  ✓
96,000,000 / 1,920 = 50,000   ✓
96,000,000 / 9,600 = 10,000   ✓
```

**⑤ 예산 여유 확인** (7-2 표 참고) → 30~70 % 사용이 무난

**→ 결론: 분주비 1,920 (틱 20us, 25,000칸, 38 % 사용).**
100us(9,600)도 충분히 유효하다 — 해상도가 목표에 비해 넉넉하기 때문.

### 7-5. 🔍 대조 — 왜 32비트 타이머는 "내 맘대로"가 통했나

**3초, TIM2(32비트):**
```
분주비 ≥ 3 × 96,000,000 / 4,294,967,295 = 0.067
→ 1 이상 (사실상 제약 없음!)
```

| | 하한 | 자유도 |
|---|---|---|
| **16비트** (TIM3/TIM4) | 빡빡함 (계산 필수) | 낮음 |
| **32비트** (TIM2/TIM5) | 거의 없음 | 높음 (아무 값이나 대체로 OK) |

**"분주비는 내 맘대로"라는 감각은 32비트 타이머에서 연습했기 때문에 생긴 것**이고,
16비트로 오면 제약이 드러난다. 그래서 **비트 폭 확인이 첫 단계**다.

### 7-6. PWM은 기준이 정반대다

```
측정 : 분주비를 "충분히 크게"  (목표 시간을 예산 안에 담아야)
PWM  : 분주비를 "최대한 작게"  (ARR을 키워 듀티 해상도 확보)
```

**PWM 절차:**
```
① 우선 PSC = 0 으로 시도
② ARR = TIMXCLK / f_PWM - 1 이 타이머 폭 안에 들어가면 확정
③ 넘치면, 넘치지 않을 만큼만 최소로 분주
```

TIM5(20 kHz): `ARR = 96,000,000/20,000 - 1 = 4,799` → 16비트에도 들어감 → **PSC = 0 확정** ✓
저주파 PWM(100 Hz): `ARR = 959,999` → 16비트 초과 → 분주 필요 (부저 TIM3가 분주한 이유)

### 7-7. ⭐ 공통 — PSC가 정수로 떨어지게 (주파수 오차 방지)

기준 주파수(CK_CNT)는 **TIMXCLK(96 MHz)의 정수 약수**여야 PSC가 딱 떨어진다.
```
96,000,000 / 1,000,000 = 96    → PSC=95 (정확) ✓
96,000,000 / 10,000,000 = 9.6  → 반올림 오차 발생 ✗
```
`+0.5`(반올림)는 안전장치일 뿐, 반올림하는 순간 실제 주파수가 목표와 미세하게 어긋난다.
→ 정밀 타이밍에선 **정수 약수**(1 MHz, 2 MHz, 8 MHz, 48 MHz…) 또는 **PWM은 PSC=0**.

### 7-8. 치트시트

**측정 / 타임아웃**
```
① 타이머 비트 폭 확인 (16 or 32)         ← 첫 단계!
② 분주비 ≥ 목표시간 × TIMXCLK / ARR_MAX   ← 하한 (필수 계산)
③ 분주비 ≤ 65,536                        ← 상한
④ 그 사이에서 틱이 깔끔한 값 (10us/20us/100us)
⑤ TIMXCLK의 약수인지 (PSC 오차 0)
⑥ 예산(ARR_MAX)의 30~70 % 사용이면 무난
```

**PWM**
```
① PSC = 0 부터 시도
② ARR = TIMXCLK/f_PWM - 1 이 폭 안에 들어가면 끝
③ 넘치면 최소한만 분주
④ 듀티 단계(=ARR+1)가 응용에 충분한지 (≥256~1000)
```

### 7-9. ⚠️ ARR 관련 실수 두 가지 (실제로 반복한 것)

`ARR`은 **"칸수(카운트 개수)"** 다. 분주비도 아니고, 시간(ms) 그 자체도 아니다.

#### 실수 A — 분주비 공식을 ARR에 사용
```c
TIM4->ARR = (unsigned int)(TIMXCLK / TIM4_FRAG + 0.5) - 1;   // ✗
```
`TIMXCLK / FRAG` 는 **분주비**를 다시 구한 것이다(= `TIM4_TICK` = 9,600).
→ ARR = 9,599 → `9,599 × 100us` = **959.9 ms** (목표 500 ms와 무관)

#### 실수 B — 시간(ms) 숫자를 ARR에 그대로 대입
```c
TIM4->ARR = 500 - 1;      // ✗  "500ms니까 500"
```
ARR의 단위는 **칸수**이지 ms가 아니다. 틱이 100us이므로
→ `500 칸 × 100us` = **50 ms** (10배 부족)

#### 올바른 계산
```c
TIM4->ARR = TIM4_PLS_OF_1ms * 500 - 1;    // ✓ 10 × 500 - 1 = 4,999
// TIM4_PLS_OF_1ms = FRAG/1000 = 10,000/1000 = 10  (1ms당 10칸)
```
검산: `(9599+1) × (4999+1) / 96,000,000 = 0.5초` ✓

#### 세 값의 구분 (핵심)
| 값 | 정체 | 출처 | 들어갈 곳 |
|---|---|---|---|
| **분주비** | 클럭 몇 개당 1칸 | 내가 정함 (7-4 절차) | `PSC` (−1) |
| **1틱** | 1칸이 몇 초인가 | `분주비 / TIMXCLK` | (중간 계산) |
| **칸수** | 몇 칸 세는가 | **목표시간 ÷ 1틱** | `ARR` (−1) |

> **`ARR`을 채울 때는 항상 "목표 시간을 1틱으로 나눈다"에서 출발**한다.
> `TIMXCLK`가 등장하는 식은 대개 PSC용이지 ARR용이 아니다.

### 7-10. ⚠️ 컨벤션 충돌 주의 (실제 발생)

`timer.h`의 낡은 정의(`TIM4_TICK = 20`, **시간 us**)와
새 컨벤션(`TIM4_TICK = 9600`, **분주비**)이 **같은 이름**이라 중복 정의 경고가 발생했다.

```
timer.c:61: warning: 'TIM4_TICK' redefined
```

**파급 효과**: 매크로는 사용 시점에 펼쳐지므로, 재정의 이후 `timer.h`의 파생 매크로가 깨진다.
```
TIME4_PLS_OF_1ms = 1000/TIM4_TICK = 1000/9600 = 0   ← 정수 나눗셈으로 0!
→ 기존 TIM4_Repeat()의 ARR 계산이 완전히 무효화됨
```
→ **한 프로젝트 안에서 컨벤션은 하나로 통일**하고, 낡은 정의는 삭제할 것.

## 8. 이 프로젝트 타이머 실제 배치 (현재 구현)

| 타이머 | 폭 | 용도 | 분주비 | 1틱 | 목표 시간 | 칸수(ARR+1) | 예산 사용률 | 상태 |
|---|---|---|---|---|---|---|---|---|
| **TIM5** | 32 | **PWM 출력**(모터) | 1 (PSC=0) | 10.4ns | 주기 50us(20kHz) | 4,800 | — | ✅ 구현 |
| **TIM2** | 32 | **3초 롱프레스** 타임아웃(인터럽트) | 1,920 | 20us | 3초 | 150,000 | 0.003% (32비트) | ✅ 구현 |
| **TIM4** | 16 | **500ms 데드타임**(방향 전환 시) | 9,600 | 100us | 500ms | 5,000 | **7.6%** | 🔧 작업 중 |
| **TIM3** | 16 | (미사용 — 원래 계획은 1000ms) | — | — | — | — | — | ⬜ 미사용 |

### 각 선택의 근거

**TIM5 (PWM)** — `PSC=0`
듀티 해상도가 기준이므로 분주 없음. `ARR = 96e6/20,000 - 1 = 4,799` → 듀티 4,800단계.
20kHz는 가청 한계를 넘어 모터 소음이 없다.

**TIM2 (3초)** — 분주비 1,920 (틱 20us)
32비트라 하한 제약이 사실상 없음(`분주비 ≥ 0.067`) → 읽기 편한 20us 틱으로 자유 선택.
`ARR+1 = 50 × 3,000 = 150,000` — 32비트 예산의 0.003%밖에 쓰지 않는다.

**TIM4 (500ms)** — 분주비 9,600 (틱 100us)
16비트라 **하한 733**이 실제 제약. 9,600은 범위 안이고, `ARR+1 = 10 × 500 = 5,000`으로
예산의 7.6%만 사용해 여유가 크다. 100us 해상도는 500ms 대비 0.02%로 넘치게 충분(7-3 참고).
> 참고: 분주비 1,920(20us, 25,000칸, 38%)도 유효하다. 둘 다 정답 범위 안이며,
> 9,600은 여유를, 1,920은 정밀도를 택한 것이다.

검산(정수 약수): `96e6/1,920 = 50,000` ✓ / `96e6/9,600 = 10,000` ✓ / PWM은 PSC=0 ✓

### 16비트 vs 32비트 — 이번 프로젝트에서 실제로 드러난 차이

| | TIM2 (32비트, 3초) | TIM4 (16비트, 500ms) |
|---|---|---|
| 분주비 하한 | 0.067 → **제약 없음** | **733** → 실제 제약 |
| 분주비 선택 | 자유 (읽기 편한 값) | 계산 필수 |
| 첫 시도 결과 | 문제없이 동작 | **48분주로 시도 → 예산 1,526% 초과 실패** |

**32비트로 연습하면 "분주비는 아무거나"라는 감각이 생기지만, 16비트에서는 반드시 계산해야 한다.**

### TIM4 구현 시 체크리스트 (7절 절차 적용)

```c
Macro_Set_Bit(RCC->APB1ENR, 2);              // ① 클럭 (TIM4 = bit2)
TIM4->CR1 = (0x1 << 4) | (0x1 << 3);         // ② DIR=1(다운) + OPM=1(원샷)
TIM4->PSC = TIM4_TICK - 1;                   //   9,599 (9,600분주)
TIM4->ARR = TIM4_PLS_OF_1ms * time - 1;      //   시간→칸수 변환 (7-9 참고)
Macro_Set_Bit(TIM4->EGR, 0);                 // ③ PSC/ARR 반영
Macro_Clear_Bit(TIM4->SR, 0);                //   EGR이 세운 UIF 청소 (순서 중요)
NVIC_ClearPendingIRQ(30);
Macro_Set_Bit(TIM4->DIER, 0);                // ④ UIE (인터럽트 허용, 2단 스위치)
NVIC_EnableIRQ(30);                          //   TIM4 = IRQ 30
Macro_Set_Bit(TIM4->CR1, 0);                 // ⑤ CEN 시작 (제일 마지막)
```

> **구조 권장**: `TIM4_Init(void)`처럼 초기화에서 바로 시작(CEN)하면 안 된다.
> 500ms 데드타임은 **방향이 바뀔 때만** 필요하므로, TIM2와 동일하게
> **`TIM4_Interrupt_Enable(int en, int time)`** 형태로 만들어 필요할 때 시작·취소하는 것이 맞다.

## 한 줄 요약

> **분주비**로 "1판(=1카운트)이 몇 초인지"를 정하고, **ARR**로 "몇 판 셀지(주기)"를 정한다.
> PWM은 여기에 **CCR**("몇 판까지 High")을 얹어 듀티(=모터 속도)를 만든다. CNT는 0부터 세니 **PSC·ARR 모두 -1**.
